### Experiment 31 — does sequence-level multi-tasking help?

This experiment isolates the effect of multi-task learning (MTL) itself, deliberately using the
simplest possible model: a single-layer LSTM over a single feature (log-return, unnormalized),
compared across three training setups. All three share seq_size=23, AdamW + CosineAnnealingLR,
and predict the next-period stock log-return; the `time_mask` feature is passed into every model
but not used in the forward pass (see `singleLSTM/Model.py`).

| variant                    | task setup                                                                 | loss                                     | best final_test_loss (of 100 runs) |
|:----------------------------|:------------------------------------------------------------------------------|:--------------------------------------------|:----------------------------------------|
| `singleLSTM`                | single task — predict only the final-timestep return                       | SmoothL1Loss (beta=3.5e-2)                 | 0.4658                                   |
| `MultiTaskSingleLSTM`                 | auxiliary task added: predict the *next* log-return at every timestep of the sequence, not just the last | SmoothL1Loss (beta=3.5e-2)                 | 0.4682                                   |
| `MultiTaskWithLossWeights`  | same auxiliary-task setup, but the 23 per-timestep losses are combined via learned uncertainty weights instead of a flat sum | SmoothL1Loss (beta=3.5e-2) + uncertainty weighting | 0.4665                                   |

- **Architecture (high-level):** `MultiTaskSingleLSTM` applies the shared output head to every LSTM timestep
  (not just the last one) and treats predicting each next step's log-return as an auxiliary task,
  with the real target appended as the final "task". `MultiTaskWithLossWeights` combines those 23
  per-timestep losses using the uncertainty-weighting scheme from *"(2018) Multi-Task Learning
  Using Uncertainty to Weigh Losses"* (see `experiments/model_architectures/papers/`): each task
  gets a learned weight `0.5 * exp(-s)` plus a `0.5 * sum(s)` regularization term. This
  regularization term is what makes `final_train_loss` legitimately negative (around -69 to -70)
  in this variant's `results.csv` — that is expected behavior of the method, not a bug.

- **Results:** All three variants land within ~0.002 of each other on `final_test_loss` — for this
  minimal single-feature setup, neither the auxiliary sequence-prediction task nor the
  uncertainty-weighted loss meaningfully outperforms the plain single-task baseline. See
  `test_performances.png` and `train_test_data_std_diff.png` for the full run-to-run comparison
  (generated by `analysis.py`).
